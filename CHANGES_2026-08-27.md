## Added: a real chat-bubble-only widget for clients who already have a website

Nothing in the previous build actually gave you a bare "just a chat bubble"
file — `public/chatbot.html` is a whole landing page. For a client who
already has their own site and only wants the floating chat bubble added to
it, I built two new files:

- **`public/widget.html`** — the same launcher + chat panel as
  `chatbot.html`, with the landing page around it stripped out. It's driven
  entirely by URL parameters (`clientId`, `dashboardUrl`, `accent`, `ink`) so
  one file serves every client, same pattern as the existing chatbot file.
  It's meant to run inside a small iframe, not be opened directly.
- **`public/embed.js`** — a one-line snippet a client with a website pastes
  once, right before `</body>`:
  ```html
  <script src="https://app.assistq.in/embed.js" data-client="abc-realty"></script>
  ```
  It injects a small floating iframe pointing at `widget.html`, and resizes
  that iframe (via `postMessage`) between a small closed bubble and the full
  chat panel size as the visitor opens/closes it — so the rest of the
  client's page stays fully clickable when the chat is closed.

## Fixed: the new widget would have been silently blocked by a security header

`server.js` sets `X-Frame-Options: SAMEORIGIN` on every response as a
security hardening measure. That's correct for the dashboard and admin
pages — but it also would have applied to `widget.html`, and
`X-Frame-Options: SAMEORIGIN` means "browsers must refuse to display this
page inside an iframe on any other domain." Since the entire point of
`widget.html` is to be iframed on a **client's own website** (a different
domain, by definition), every embed would have failed silently — the iframe
would just render blank, with a console error the client would never see.

I excluded only `/widget.html` from that header; every other route (the
dashboard, login, admin pages, all `/api/*` routes) keeps the original
`SAMEORIGIN` protection unchanged.
